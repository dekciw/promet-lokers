## Phase 1: Frontend MVP ✓

**Goal:** Рабочий конфигуратор с реальными данными, diff-логикой и базовым расчётом цены.

**Status:** ✓ Выполнено (2026-04-01)

**Закрывает требования:** CONF_1–14, DOC_6, UX_1, UX_2

**Что реализовано:**
- `App.jsx` — state поднят, config передаётся через props
- `src/utils/calcDiff.js` — diff по 10 полям
- `src/api/loadCatalog.js` — загрузка каталога из Firebase Firestore REST API
- Configurator: три колонки, анимации строк (0.4s cubic-bezier)
- Parameters: 11 блоков управления параметрами со степпером ±50мм
- Header: логотип Промет, декоративные города, фон #0C53B3, высота 99px
- Кнопки КП/НЗ заблокированы без выбранной модели

### Phase Details

#### Phase 7: Foundation
**Goal**: Администратор видит и использует /admin, обычные пользователи не могут туда попасть, все записи в Firestore и Storage защищены правилами
**Depends on**: Phase 5 (авторизация уже работает через Firebase Auth)
**Requirements**: ROUTE-01, ROUTE-02, ROUTE-03, ACCESS-01, ACCESS-02, SEC-01, SEC-02
**Success Criteria** (what must be TRUE):
  1. Пользователь admin@promet.ru видит кнопку «Админ» в интерфейсе и переходит на /admin
  2. Обычный пользователь (не admin@promet.ru) не видит ссылку /admin и при прямом URL-переходе редиректится на /configurator
  3. Администратор может вернуться к конфигуратору из /admin одним кликом
  4. Попытка записи в Firestore catalog/main от имени обычного пользователя возвращает PERMISSION_DENIED
  5. Попытка загрузить файл в Firebase Storage от имени обычного пользователя возвращает PERMISSION_DENIED
**Plans**: 2 plans
Plans:
- [x] 07-01-PLAN.md — React Router v7 Setup + ProtectedRoute + AdminPage placeholder
- [ ] 07-02-PLAN.md — Firebase Security Rules: Firestore write + Storage
**UI hint**: yes

#### Phase 8: Catalog CRUD
**Goal**: Администратор может просматривать весь каталог, находить нужные модели и редактировать, добавлять или удалять их через интерфейс /admin
**Depends on**: Phase 7
**Requirements**: CATALOG-01, CATALOG-02, CATALOG-03, CATALOG-04, CATALOG-05, CATALOG-06, CATALOG-07, CATALOG-08
**Success Criteria** (what must be TRUE):
  1. Администратор видит все шкафы каталога на /admin, может фильтровать по серии (ML / LS / Все) и искать по названию
  2. При клике на карточку открывается попап со всеми 14 полями (порядковый номер, название, артикул, серия, цена, высота, ширина, глубина, толщина корпуса, толщина двери, количество замков, количество дверей, вес, cpBezNDS), изменения сохраняются в Firestore
  3. Администратор может добавить новую карточку шкафа с заполнением всех обязательных полей — после сохранения карточка появляется в списке
  4. Администратор может удалить карточку с подтверждением — после удаления она исчезает из списка и из Firestore
**Plans**: TBD
**UI hint**: yes

#### Phase 9: Media & Ordering
**Goal**: Администратор может загрузить фото шкафа прямо из попапа редактирования, и может менять порядок шкафов в списке перетаскиванием
**Depends on**: Phase 8
**Requirements**: MEDIA-01, MEDIA-02, MEDIA-03, MEDIA-04, ORDER-01, ORDER-02, ORDER-03
**Success Criteria** (what must be TRUE):
  1. Администратор выбирает файл в попапе — перед загрузкой фото авторесайзится до высоты 1520px (Canvas API), загружается в Firebase Storage, URL записывается в поле photoUrl модели в Firestore
  2. Генератор КП использует photoUrl из Firestore если он есть; при его отсутствии — fallback на /img/models/{modelId}.png
  3. Администратор перетаскивает карточку шкафа в новую позицию — новый порядок сохраняется в Firestore через поле sortOrder каждой модели
  4. Список моделей в конфигураторе (для обычных пользователей) отображается в порядке sortOrder
**Plans**: TBD
**UI hint**: yes

#### Phase 10: Price Coefficients
**Goal**: Администратор может просматривать и редактировать все коэффициенты расчёта цены прямо в интерфейсе /admin, без правок в Google Sheets или коде
**Depends on**: Phase 7
**Requirements**: PRICE-01, PRICE-02, PRICE-03, PRICE-04, PRICE-05, PRICE-06
**Success Criteria** (what must be TRUE):
  1. На отдельной вкладке /admin администратор видит все надбавки: вентиляция, толщина 0.6/0.7 мм (ML и LS отдельно), глубина (по сериям и qty-брекетам), высота (по сериям)
  2. Администратор редактирует любое числовое значение в поле ввода
  3. Кнопка «Сохранить» сохраняет все изменённые коэффициенты в Firestore одним запросом
  4. После сохранения конфигуратор использует обновлённые коэффициенты при следующем расчёте цены
**Plans**: TBD
**UI hint**: yes

#### Phase 11: Users & History
**Goal**: Администратор управляет учётными записями пользователей через UI; обычные пользователи видят историю скачанных КП и могут восстановить конфигурацию
**Depends on**: Phase 7
**Requirements**: USERS-01, USERS-02, USERS-03, USERS-04, HIST-01, HIST-02, HIST-03, HIST-04
**Success Criteria** (what must be TRUE):
  1. Администратор видит список всех пользователей системы на отдельной вкладке /admin
  2. Администратор создаёт новый аккаунт (email + пароль) через Cloud Function — новый пользователь появляется в списке и может войти в систему
  3. Администратор удаляет (деактивирует) аккаунт через Cloud Function — пользователь больше не может войти
  4. При скачивании КП конфигурация автоматически сохраняется в /users/{uid}/history (дата, модель, цена)
  5. Пользователь видит список своих КП и может восстановить конфигурацию или повторно скачать КП одним кликом
**Plans**: 4 plans
Plans:
- [x] 11-01-PLAN.md — useUsersAdmin hook + secondary Firebase App pattern + tests (USERS-01..04)
- [x] 11-02-PLAN.md — useHistory hook + Firestore subcollection + tests (HIST-01..04)
- [ ] 11-03-PLAN.md — UsersTab UI + AdminPage tab + LoginScreen status gate (USERS-01..03)
- [ ] 11-04-PLAN.md — HistoryPage + saveToHistory in Configurator + uid flow + Header link (HIST-01..04)
