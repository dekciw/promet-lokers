# GSD — Полная энциклопедия команд

> **Что такое GSD?**
> Get Shit Done — система управления разработкой поверх Claude Code. Разбивает проект на фазы, следит за контекстом между сессиями, управляет планами и верификацией. Все артефакты хранятся в `.planning/`.

---

## Быстрый старт — типичный рабочий цикл

```
Новая фича:
/gsd:discuss-phase → /gsd:plan-phase → /gsd:execute-phase → /gsd:verify-work → /gsd:ship

Баг непонятен:
/gsd:do "описание проблемы"   или   /gsd:debug

Не знаешь что делать дальше:
/gsd:progress   или   /gsd:next
```

## 1. Навигация и ориентация

### `/gsd:progress`
**Что делает:** Показывает текущее состояние проекта — какая фаза активна, что сделано, что заблокировано — и подсказывает следующий шаг.

**Когда использовать:**
- В начале новой сессии чтобы восстановить контекст
- Когда не помнишь на чём остановился
- Когда хочешь сводку без лишних деталей

**Пример для Промет:**
```
/gsd:progress
→ Phase 2 waiting — ждёт формулу цены от менеджеров
→ Следующий шаг: получить коэффициенты и реализовать calcPrice
```

---

### `/gsd:next`
**Что делает:** Автоматически определяет следующий логичный шаг в воркфлоу и переходит к нему без вопросов.

**Когда использовать:**
- Когда хочешь чтобы GSD сам решил что делать дальше
- Быстрый переход между этапами фазы

**Отличие от `/gsd:progress`:** progress показывает — next действует.

---

### `/gsd:do`
**Что делает:** Роутер. Принимает свободный текст, сам определяет нужную GSD-команду и выполняет её.

**Когда использовать:**
- Когда не знаешь какую команду использовать
- Когда не уверен это баг, фича или что-то другое
- Для быстрого старта без выбора команды вручную

**Примеры:**
```
/gsd:do кнопка КП не активируется при выбранной модели
→ GSD решает: это баг → запускает /gsd:debug

/gsd:do хочу добавить историю заказов
→ GSD решает: новая фича → запускает /gsd:discuss-phase

/gsd:do что осталось до релиза
→ GSD решает: нужна сводка → запускает /gsd:progress
```

---

### `/gsd:stats`
**Что делает:** Показывает статистику проекта — количество фаз, планов, требований, коммитов, временную шкалу.

**Когда использовать:** Когда нужна сводка прогресса для себя или для показа стейкхолдеру.

---

### `/gsd:help`
**Что делает:** Показывает список всех доступных GSD-команд с кратким описанием.

**Когда использовать:** Когда не помнишь название нужной команды.

## 2. Полный цикл фазы

### `/gsd:discuss-phase`
**Что делает:** Задаёт тебе серию вопросов о фиче перед планированием. Собирает требования, ограничения, edge-кейсы, чтобы план получился точным.

**Когда использовать:**
- Перед любой новой фичей когда детали ещё не ясны
- Когда фича затрагивает несколько компонентов
- Когда есть неопределённость в требованиях

**Что создаёт:** Контекст для последующего `/gsd:plan-phase`

**Пример для Промет:**
```
/gsd:discuss-phase
→ "Какую фичу хочешь добавить?"
→ "Где хранить историю — Firebase или localStorage?"
→ "Сколько конфигураций на пользователя?"
→ После ответов → готов к /gsd:plan-phase
```

**Флаг `--auto`:** Пропускает вопросы, Claude выбирает дефолтные ответы самостоятельно.
```
/gsd:discuss-phase --auto
```

---

### `/gsd:plan-phase`
**Что делает:** Создаёт детальный `PLAN.md` в `.planning/phases/` — разбивает фичу на конкретные задачи с зависимостями, порядком выполнения и критериями успеха.

**Когда использовать:** После `discuss-phase` или когда задача уже ясна и нужна декомпозиция.

**Что создаёт:** `PLAN.md` файл вида `.planning/phases/02-price-formula/02-01-calcprice-PLAN.md`

**Пример для Промет:**
```
/gsd:plan-phase
→ Задача 1: занести коэффициенты в Firebase
→ Задача 2: реализовать calcPrice(config, catalog)
→ Задача 3: написать тесты на 5 реальных примерах
→ Создаёт PLAN.md → можно проверить и запустить execute
```

---

### `/gsd:execute-phase`
**Что делает:** Выполняет всё что написано в `PLAN.md`. Запускает независимые задачи параллельно, зависимые — последовательно. Делает атомарные git-коммиты после каждой задачи.

**Когда использовать:** Когда `PLAN.md` готов и утверждён тобой.

**Что делает под капотом:**
1. Читает PLAN.md
2. Строит граф зависимостей
3. Запускает волны выполнения (Wave 1 — независимые, Wave 2 — зависящие от Wave 1)
4. Коммитит каждую выполненную задачу
5. Обновляет STATE.md

**Важно:** Не запускай без проверки PLAN.md — это основная команда "сделай всё".

---

### `/gsd:verify-work`
**Что делает:** Интерактивная UAT-сессия. Claude задаёт тебе вопросы и ты проверяешь фичу в браузере в реальном времени. Фиксирует что работает, что нет.

**Когда использовать:** После `execute-phase` — финальная проверка перед ship.

**Пример:**
```
/gsd:verify-work
→ "Открой конфигуратор, выбери серию ML"
→ "Измени ширину на 500мм — появилась оранжевая обводка?"
→ "Нажми копировать артикул — скопировалось?"
→ Фиксирует результаты → готово к /gsd:ship
```

## 3. Выполнение и верификация

### `/gsd:quick`
**Что делает:** Выполняет задачу с GSD-гарантиями (атомарные коммиты, обновление STATE.md) но без полного цикла планирования. Пропускает необязательные агенты.

**Когда использовать:**
- Небольшая понятная задача которую не нужно планировать
- Быстрый фикс или tweakUI
- Когда хочешь GSD-порядок без overhead'а

**Отличие от `/gsd:execute-phase`:** Не требует PLAN.md, сразу приступает к работе.

**Пример для Промет:**
```
/gsd:quick поменять placeholder в поле ширины с "Ширина" на "Ширина, мм"
```

---

### `/gsd:fast`
**Что делает:** Минимальный режим. Выполняет тривиальную задачу инлайн без субагентов и планирования.

**Когда использовать:**
- Совсем простые задачи (переименовать переменную, поменять цвет, добавить className)
- Когда нужно максимально быстро

**Отличие от `/gsd:quick`:** Ещё проще — ни субагентов, ни STATE-обновлений.

```
/gsd:fast переименовать переменную `val` в `price` в calcPrice.js
```

---

### `/gsd:validate-phase`
**Что делает:** Ретроспективный аудит завершённой фазы. Проверяет что всё реализовано и тесты покрывают требования (Nyquist-валидация).

**Когда использовать:** Если фаза завершена но хочешь убедиться что ничего не пропущено перед переходом к следующей.

## 4. UI-специфичные

### `/gsd:ui-phase`
**Что делает:** Генерирует `UI-SPEC.md` — дизайн-контракт для UI-фазы. Фиксирует компоненты, цвета, отступы, состояния, анимации **до написания кода**. Использует скилл UI UX Pro Max.

**Когда использовать:**
- Перед созданием нового UI-блока с нуля
- Когда нужно согласовать дизайн перед реализацией
- При планировании фичи с нетривиальным UI

**Пример для Промет:**
```
/gsd:ui-phase
→ "Опиши компонент PDF-кнопок"
→ Создаёт UI-SPEC.md: состояния (disabled/hover/active), цвета из дизайн-системы, анимации
→ Потом /gsd:plan-phase использует этот спек
```

---

### `/gsd:ui-review`
**Что делает:** Аудит **уже написанного** UI-кода по 6 критериям: визуал, accessibility, типографика, цвета, анимации, адаптивность. Выдаёт оценку PASS/FLAG/BLOCK по каждому.

**Когда использовать:**
- После написания нового компонента
- Когда что-то выглядит "не так" но непонятно что
- Перед `/gsd:ship` для UI-фич

**Пример для Промет:**
```
/gsd:ui-review
→ Контраст текста на синем фоне: PASS (7.2:1)
→ Touch target кнопки степпера: FLAG (38px < 44px)
→ prefers-reduced-motion: PASS
```

## 5. Отладка

### `/gsd:debug`
**Что делает:** Открывает структурированную debug-сессию с постоянным состоянием. Применяет научный метод: симптом → гипотеза → эксперимент → вывод. Сохраняет прогресс расследования между сообщениями.

**Когда использовать:**
- Баг не воспроизводится стабильно
- Проблема затрагивает несколько файлов
- Уже потратил время и не нашёл причину
- Нужно системное расследование, а не угадывание

**Как работает:**
```
/gsd:debug
→ "Опиши симптом и шаги для воспроизведения"
→ Claude формирует гипотезы
→ Проверяет каждую методично
→ Сохраняет checkpoint если контекст кончается
→ /gsd:resume-work продолжает с того же места
```

**Используется совместно со скиллом `debugging-strategies`** — автоматически применяет систематический подход.

**Пример для Промет:**
```
/gsd:debug
→ Симптом: степпер показывает неверный шаг после сброса параметров
→ Гипотеза 1: isSliding не сбрасывается при reset
→ Проверяем App.jsx:handleReset → нашли
```

---

### `/gsd:forensics`
**Что делает:** Post-mortem анализ сломанного GSD-воркфлоу. Читает git-историю, артефакты `.planning/`, STATE.md и восстанавливает что пошло не так.

**Когда использовать:** Если GSD-сессия зависла, PLAN.md повреждён, или execute-phase прервалась на середине и непонятно что выполнено.

---

## 6. Управление проектом

### `/gsd:ship`
**Что делает:** Финальный цикл перед отправкой кода. Запускает review, проверки, применяет скилл `security-auditor`, создаёт PR на GitHub.

**Когда использовать:** Когда фича готова и протестирована — последний шаг цикла.

**Что делает под капотом:**
1. Проверяет что все задачи PLAN.md выполнены
2. Запускает security-auditor (XSS, открытые ключи, Firebase rules)
3. Создаёт PR с описанием изменений
4. Обновляет STATE.md

**Пример для Промет:**
```
/gsd:ship
→ Проверяет: API-ключ не в коде ✅
→ Проверяет: Firestore rules только чтение ✅
→ Создаёт PR: "feat: Phase 3 PDF export"
```

---

### `/gsd:add-phase`
**Что делает:** Добавляет новую фазу в конец текущего milestone в ROADMAP.md.

**Когда использовать:** Когда появляется новая крупная задача которой нет в роадмапе.

**Пример для Промет:**
```
/gsd:add-phase
→ "Название фазы?"
→ "Phase 5 — Performance Audit"
→ Добавляет в ROADMAP.md с шаблоном Goal/Status/Milestones
```

---

### `/gsd:insert-phase`
**Что делает:** Вставляет срочную фазу между существующими с дробной нумерацией (например 2.1 между Phase 2 и Phase 3).

**Когда использовать:** Срочная задача которую нельзя ждать но и нельзя сдвигать существующие фазы.

```
/gsd:insert-phase
→ Phase 2.1 — Hotfix авторизации (вставляется между Phase 2 и Phase 3)
```

---

### `/gsd:remove-phase`
**Что делает:** Удаляет будущую фазу из ROADMAP.md и перенумеровывает последующие.

**Когда использовать:** Требование стало неактуальным или вынесено в другой проект.

---

### `/gsd:complete-milestone`
**Что делает:** Архивирует завершённый milestone, обновляет PROJECT.md, готовит почву для нового цикла.

**Когда использовать:** Когда все фазы текущего milestone выполнены и верифицированы.

**Пример для Промет:** После завершения Phase 4 (Auth + History) — архивировать Milestone 1 и начать Milestone 2.

---

### `/gsd:audit-milestone`
**Что делает:** Аудит milestone перед архивацией — проверяет что все требования действительно закрыты, ничего не пропущено.

**Когда использовать:** Перед `/gsd:complete-milestone` для уверенности.

---

### `/gsd:milestone-summary`
**Что делает:** Генерирует читаемый summary завершённого milestone — для себя, для команды, для стейкхолдера.

**Пример вывода:**
```
Milestone 1 — MVP Конфигуратора
✅ 14/14 функциональных требований
✅ Firebase + Google Sheets интеграция
✅ Расчёт цены в реальном времени
⏳ Phase 2 формула ждёт менеджеров
```

---

### `/gsd:health`
**Что делает:** Диагностирует состояние `.planning/` директории — ищет повреждённые файлы, несоответствия STATE.md и ROADMAP.md, предлагает ремонт.

**Когда использовать:** Если что-то в GSD работает странно или после ручного редактирования файлов.

## 7. Заметки и идеи

### `/gsd:note`
**Что делает:** Мгновенная фиксация идеи без оформления. Просто добавляет заметку. Можно потом продвинуть в todo или backlog.

```
/gsd:note добавить анимацию появления sticky-плашки на мобильных
/gsd:note спросить у менеджеров про срок действия КП — 30 или 60 дней?
```

---

### `/gsd:add-todo`
**Что делает:** Создаёт оформленный TODO из текущего контекста разговора — с описанием, приоритетом, привязкой к фазе.

**Когда использовать:** Когда замечаешь задачу в процессе работы и не хочешь её потерять.

---

### `/gsd:check-todos`
**Что делает:** Показывает все pending TODO и помогает выбрать следующий.

---

### `/gsd:add-backlog`
**Что делает:** Отправляет идею в backlog с нумерацией 999.x — паркует без блокировки текущей работы.

**Когда использовать:** Хорошая идея, но не сейчас.

```
/gsd:add-backlog 3D-превью шкафа (высокая стоимость, после фокус-группы)
```

---

### `/gsd:review-backlog`
**Что делает:** Показывает backlog и помогает продвинуть элементы в активный milestone.

---

### `/gsd:plant-seed`
**Что делает:** Фиксирует идею с условием активации — "всплывёт автоматически когда наступит нужный milestone".

```
/gsd:plant-seed рассмотреть PWA когда будет Phase 4 (Auth)
→ Идея появится в контексте когда ты дойдёшь до Phase 4
```

---

## 8. Сессии и контекст

### `/gsd:resume-work`
**Что делает:** Восстанавливает контекст предыдущей сессии — читает STATE.md, PLAN.md, последние коммиты — и продолжает с того места где остановился.

**Когда использовать:** В начале каждой новой сессии если работа была прервана.

```
/gsd:resume-work
→ "На прошлой сессии: реализован степпер, осталось: sticky-плашка на мобильных"
→ Готов продолжать
```

---

### `/gsd:pause-work`
**Что делает:** Создаёт handoff-документ при прерывании работы — фиксирует где остановился, что сделано, что осталось, open questions.

**Когда использовать:** Перед тем как закрыть сессию на середине фазы.

---

### `/gsd:session-report`
**Что делает:** Генерирует отчёт сессии — что сделано, сколько токенов потрачено (примерно), итоги.

---

### `/gsd:thread`
**Что делает:** Управляет персистентными контекстными тредами для длинной работы через несколько сессий.

---

## Скиллы — автоматически по триггеру

Скиллы не команды — они подключаются автоматически когда Claude видит нужный контекст. Правила в `CLAUDE.md`.

| Скилл | Триггер | Что даёт |
|---|---|---|
| `ui-ux-pro-max` | Любая работа с компонентами/CSS | 67 стилей, 96 палитр, UX-правила |
| `context7-mcp` | Код с React/Firebase/react-hook-form | Актуальная документация |
| `debugging-strategies` | Баг, ошибка, `/gsd:debug` | Системный подход к отладке |
| `security-auditor` | `/gsd:ship`, Firebase rules, зависимости | OWASP, проверка Firebase, XSS |

## Карта команд по ситуации

| Ситуация | Команда |
|---|---|
| Начало сессии — восстановить контекст | `/gsd:resume-work` или `/gsd:progress` |
| Не знаю что делать дальше | `/gsd:next` |
| Новая фича — требования не ясны | `/gsd:discuss-phase` |
| Новая фича — требования ясны | `/gsd:plan-phase` |
| Фича с нетривиальным UI | `/gsd:ui-phase` → `/gsd:plan-phase` |
| Выполнить план | `/gsd:execute-phase` |
| Маленькая задача без плана | `/gsd:quick` |
| Совсем тривиальная правка | `/gsd:fast` |
| Проверить что сделал | `/gsd:verify-work` |
| Аудит UI-кода | `/gsd:ui-review` |
| Отправить PR | `/gsd:ship` |
| Непонятный баг | `/gsd:debug` |
| Не знаю баг это или нет | `/gsd:do "описание"` |
| Быстрая идея | `/gsd:note` |
| Идея на потом | `/gsd:add-backlog` |
| Сломался GSD-воркфлоу | `/gsd:forensics` |

## Артефакты GSD в проекте

```
.planning/
├── PROJECT.md          ← описание продукта, требования, решения
├── ROADMAP.md          ← фазы, статусы, milestones
├── STATE.md            ← текущее состояние, что реализовано, decisions log
├── REQUIREMENTS.md     ← полный список требований
├── phases/
│   ├── 01-frontend-mvp/
│   │   ├── 01-01-data-layer-PLAN.md
│   │   └── 01-UAT.md
│   └── 02-ux-improvements/
│       └── 02-UAT.md
└── codebase/
    ├── CURRENT_STATE.md    ← snapshot кодовой базы
    ├── ARCHITECTURE.md
    ├── CONVENTIONS.md
    └── STACK.md
```
